# 40-session Observability Engineering For Multi-Agent Harness Engineering

This 40 workshop (*"W" is for "workshop", eg W1 is Workshop 1) curriculum deliberately does not make anyone "fluent" in anything ... but completing W1–W8 will give you a control group; W9–W18 make you go deep enough in one framework to generate real judgment; W19–W26 show you how the deployment environment rewrites the rules of security and evidence; W27–W34 turn security from "configuration" into "runtime adjudication"; W35–W40 compress experience into a transferable judgment tool. If the audit schemas you produce at W15 and W37 are solid, the 40 workshops have succeeded — because your first reaction to any new framework afterward will be something like "how do this system's checkpoint feed my schema," rather than just "how many GitHub stars does it have."

**The course is feasible, but understand what the goal is.** 20 days × 6 hours = 120 hours, 40 workshops. That is not enough to reach production-grade fluency in any single framework, let alone "master" all competitors in that framework's industry. But it is enough to build a **transferable judgment framework** in which you learn how to ask smarter, shrewder, tougher questions ... specifically, after completing this workshop [and extending it for your own specific interests/use cases], you should be able to ask useful questions about where each orchestration model leaks on observability and security, why it leaks, and what patches the leak. The take away should not be "I know LangGraph." It should be "I can tell, within an hour or two of experimenting and using, where a new framework's audit evidence chain breaks."

The sequence below is **depth first, breadth second, attack-and-defend throughout**. LangGraph gets ~40%, competitors and contrasts ~30%, security and observability woven through ~30%. 

Every workshop has a concrete deliverable ... there's no "just watch some YouTube vids on how to do this" — to complete the workshop you have to build something concrete that actually works and you can show to others.

### Phase 1: Foundations and Comparison Anchors (Day 1–4, 8 workshops)

Goal: build your **control group**. If you only learn LangGraph, you cannot judge whether its checkpoint is strong or weak. You must hand-build a primitive baseline first, then a CrewAI contrast.

| Day | Workshop | Topic | Core deliverable |
|:---|:---|:---|:---|
| 1 | W1 | **Hand-write a state-machine agent**: no framework, Python dict + file persistence, a 3-node workflow, manually log every step's input/output | A "nothing is helping you" baseline against which all framework gains/costs are measured |
| 1 | W2 | **Inject failure into it**: kill the process after step 2, observe what you lost; hand-roll a crude checkpoint recovery | Firsthand experience of "the cost of no checkpoint"; the minimum necessary checkpoint information |
| 2 | W3 | **CrewAI quick start**: define 3 role agents, run a sequential crew, add print/log inside a task to observe actual behavior | Feel the speed advantage of role abstraction and the black-box feel of its logging |
| 2 | W4 | **CrewAI failure injection**: kill after task 2, observe recovery behavior; try to trace a tool-call chain inside a single task | A "CrewAI audit gap list" to serve as a contrast artifact later |
| 3 | W5 | **LangGraph minimal graph**: rebuild W1's 3-node flow with StateGraph, use MemorySaver for checkpointing | Compare W1's hand-written line count against LangGraph's explicit declaration |
| 3 | W6 | **Dissect a LangGraph checkpoint**: export full state history with `getStateHistory`, read `values`/`next`/`metadata.writes`/`parentConfig` field by field | A checkpoint schema note marking which fields are audit evidence vs. runtime convenience |
| 4 | W7 | **CrewAI vs LangGraph on the same task**: implement the same "research–analyze–write report" flow in both, record token consumption, failure recovery behavior, log readability | A comparison matrix filled with your own measurements, not tutorial claims |
| 4 | W8 | **Microsoft Agent Framework as a third reference point**: read the official comparison docs, run a minimal data-flow workflow, focus on how its "graph" concept differs from LangGraph's | Understand that "directed graph" is not unique to LangGraph, but checkpoint semantics differ per vendor |

### Phase 2: Deep Dive on LangGraph Observability and Persistence (Day 5–9, 10 workshops)

Goal: push LangGraph's checkpoint from "I know it exists" to "I can audit it, replay it, and judge the strength of the evidence."

| Day | Workshop | Topic | Core deliverable |
|:---|:---|:---|:---|
| 5 | W9 | **Durability three-mode experiment**: run the same graph with `exit`/`async`/`sync`, kill mid-run, record what each mode loses | A curve of "how much evidence you buy with how much performance" |
| 5 | W10 | **Replay hands-on**: replay from a specific checkpoint_id, observe which nodes skip and which LLM calls re-fire | Understand "replay is not free" — auditing replay itself has token cost |
| 6 | W11 | **Checkpoint backend swap**: MemorySaver → SqliteSaver → PostgresSaver, observe write latency and crash-recovery differences | Pick your default audit storage backend and record the rationale |
| 6 | W12 | **DeltaChannel experiment (if available)**: build a multi-turn conversation graph, compare state growth between standard checkpointing and delta mode | Quantify the O(N²) problem; produce a "storage strategy for long audit sessions" note |
| 7 | W13 | **Wire up LangSmith**: connect LangSmith tracing, run a graph with tool calls, read the LLM and tool calls in the trace | A "what LangSmith gives / does not give" list; the commercial coupling boundary made explicit |
| 7 | W14 | **Self-built trace without LangSmith**: instrument node enter/exit, tool calls, LLM token consumption with OpenTelemetry by hand | A vendor-neutral trace skeleton, comparable side-by-side with LangSmith |
| 8 | W15 | **Audit trail design workshop**: based on W6/W9/W14 outputs, design a "presentable" audit record schema — which events, who signs, how tamper-evident, retention period | An audit evidence model document. This is one of the true core deliverables of the course |
| 8 | W16 | **Audit replay vs. re-execution**: distinguish "read checkpoint and display history" from "actually re-execute"; experiment on nodes with external API calls to see side-effect differences | Understand replay's security risk: what happens if you replay a payment node |
| 9 | W17 | **Human-in-the-loop interrupt auditing**: pause a node with `interrupt()`, record who approved, when, what exactly; test behavior when approval times out | An approval event log format, wired into W15's schema |
| 9 | W18 | **Competitor quick look: AutoGen's conversational coordination**: run a GroupChat, observe whether the conversation history is a natural audit log, and how hard it is to distinguish "said but didn't do" from "did but didn't say" | Understand "conversation record ≠ execution record" |

### Phase 3: Cloudflare and Edge Security Contrast (Day 10–13, 8 workshops)

Goal: LangGraph is a "graph runtime"; Cloudflare Agents is a "stateful micro-server." Their security boundaries are fundamentally different. This phase shows you how **the deployment environment itself becomes part of observability and security.**

| Day | Workshop | Topic | Core deliverable |
|:---|:---|:---|:---|
| 10 | W19 | **Minimal Cloudflare Agent**: deploy an `Agent` subclass, persist state with `this.state` and `this.sql`, understand "each instance is an independent micro-server" | A running edge-persistent instance |
| 10 | W20 | **Durable execution contrast**: implement a recoverable 3-step flow with `runFiber`/`stash`, contrast with LangGraph checkpoints: who stores what, where recovery granularity differs | A "cloud edge persistence vs. graph checkpoint" comparison table |
| 11 | W21 | **AI Gateway logging and auditing**: call a model via `env.AI.run()`, set `collectLog: true`, retrieve request logs with `aiGatewayLogId` and `getLog()` | Understand "model-call-layer logs" and "orchestration-layer checkpoints" are two different evidence sources |
| 11 | W22 | **Gateway feedback loop**: use `patchLog` to attach feedback/score to a log entry, simulating how human review writes into the audit chain | An "online eval → audit marking" pipeline prototype |
| 12 | W23 | **Cloudflare security boundary experiment**: from one Agent instance, try to reach another instance's SQL; record how the attempt fails | A measured note on edge isolation boundaries |
| 12 | W24 | **MCP client security**: connect an external MCP server via Cloudflare's MCP Client API, record the tool list it exposes, ask "who approved this server being connected" | An MCP onboarding review checklist |
| 13 | W25 | **Cross-platform audit stitching**: take W21's Gateway logs, W15's LangGraph audit schema, and W19's Cloudflare state-change log, design a correlation-ID-based stitching scheme | Your first practical "street smart" artifact: knowing where evidence is scattered and how to sew it together |
| 13 | W26 | **Failure drill: Cloudflare instance hibernation**: let an instance hibernate and wake, observe state and in-flight task behavior | Understand the gap between "edge environment's persistence promise" and "graph runtime's checkpoint promise" |

### Phase 4: Security Engineering — From Logs to Defense (Day 14–17, 8 workshops)

Goal: logs are not security. This phase drills attack-surface identification and least-privilege runtime execution.

| Day | Workshop | Topic | Core deliverable |
|:---|:---|:---|:---|
| 14 | W27 | **Five mandatory agent log categories**: following OWASP/NCSC guidance, fill in your LangGraph graph's logs for inputs, outputs, tool calls, retrievals, and privilege-escalation events | A logging middleware covering all five event classes |
| 14 | W28 | **Tool-call anomaly detection rules**: using W27's logs, write 3 rules — tools called that the task doesn't need, data sent to writable tools, newly appearing MCP servers | A minimal detection rule set, validated against historical logs |
| 15 | W29 | **Zero Trust middleware experiment**: in the style of AgentSudo, add JIT token + intent keyword review + hourly budget to a tool call | Experience "permission is not static config, it is a per-request adjudication" |
| 15 | W30 | **Budget-exhaustion attack drill**: construct a scenario that drives the agent into a loop of paid tool calls; intercept with W29's budget control | Understand "Denial of Wallet" as a first-class agent security threat |
| 16 | W31 | **Prompt injection's audit visibility**: inject a malicious instruction into a tool return, observe whether it appears in your logs, in what form, and whether your detection rules fire | An "injection visibility in the evidence chain" assessment |
| 16 | W32 | **Memory/context poisoning detection**: modify a state field in a checkpoint (simulating poisoning), observe downstream node behavior changes, design a state-integrity check | Understand the checkpoint as both recovery tool and attack surface |
| 17 | W33 | **Security audit workshop (part 1)**: take one complete flow from your first 32 workshops and do a threat model — assets, trust boundaries, attacker capabilities, existing controls, gaps | A threat model document |
| 17 | W34 | **Security audit workshop (part 2)**: based on W33, write 3 executable detection/interception rules, and test whether they misfire on normal flows | A runnable security-control prototype |

### Phase 5: Convergence — From "Knowing the Options" to "Asking Better Questions" (Day 18–20, 6 workshops)

Goal: stop chasing more frameworks; harden your comparison capability into a reusable judgment tool.

| Day | Workshop | Topic | Core deliverable |
|:---|:---|:---|:---|
| 18 | W35 | **Build a framework evaluation cheat sheet**: from W1–W34 measurements, fill a 5-framework × 6-dimension table (recovery granularity, nativity of audit evidence, observability coupling, security defaults, token efficiency, migration cost) | Your own evaluation matrix, not a copied one |
| 18 | W36 | **"30-minute evaluation of a new framework" drill**: given a framework you haven't used (e.g., Strands or PydanticAI), do a rapid survey with W35's dimensions and produce a one-page judgment | Validate whether the cheat sheet transfers |
| 19 | W37 | **Final audit schema**: consolidate W15/W25/W27/W32 outputs, publish your personal agent audit evidence model v1.0 | The core asset you take away |
| 19 | W38 | **Red-team drill**: use W37's schema to audit a deliberately "misbehaving" agent; check whether your schema makes the bad behavior visible and attributable | Test the real coverage of your audit design |
| 20 | W39 | **Cost–evidence tradeoff calculation**: using W9/W12/W21 data, do the math — how much extra storage/latency/tokens your audit scheme costs per day, and whether the evidence-strength gain is worth it | A tradeoff memo you can hand to a decision-maker |
| 20 | W40 | **The "smart questions" list**: write 20 questions you will ask of any future agent framework/platform, categorized by observability and security | The course's final output: not answers, but better questions |
