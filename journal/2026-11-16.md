## 0. What you are actually building

Three collaborating layers, and it matters that you can name them:

| Layer | Code | Responsibility | Knows about |
|---|---|---|---|
| **Nodes** (business logic) | `node_gather`, `node_process`, `node_finalize` | Do work, return new state, choose the successor | The domain |
| **Runner** (control plane) | `run_agent` | Loop, guard rails, timing, logging, checkpointing | Nodes *by name* only |
| **Persistence** (I/O) | `save_checkpoint`, `load_checkpoint`, `append_step_log` | Bytes on disk, atomicity, format | Nothing about the domain |

The whole design is one idea repeated: **the state dict is the only channel between steps.** Nodes do not call each other, do not share globals, and do not know what ran before them. They receive a dict and return a dict. That is what makes the thing resumable, testable, and inspectable.

```
  starting_state = {"topic": ..., "next_node": "gather", "status": "running"}
        |
        v
  node_gather ------ next_node = "process"
        |
        v
  node_process ----- attempt 1: next_node = "process"   [self-loop: it re-runs]
        |
        v
  node_process ----- attempt 2: next_node = "finalize"
        |
        v
  node_finalize ---- next_node = None   -->  `while` condition fails, loop exits
        |
        v
  final_state = {"status": "completed", "final_output": ...}

  every arrow also: appends 1 line to agent_trace.jsonl
                    and atomically rewrites agent_state.json
```

## 1. The contract (memorise these five before reading code)

1. **`next_node` is the only routing signal.** A string key into the `nodes` registry, or `None` to stop. Nothing else may end the loop.
2. **Every node returns a dict that still contains `next_node`.** A node that forgets it silently strands the run (the loop exits, `status` still says `"running"`).
3. **Only the runner writes `step_count`.** Nodes must never touch it, or the budget guard and the log numbering both lie.
4. **State must be JSON-serialisable.** No `datetime`, `set`, `bytes`, or model objects — because the checkpoint *is* `json.dump(state)`.
5. **All side effects live inside nodes.** No I/O in the runner and none at import time. That is what makes replay from a checkpoint meaningful.

If you remember nothing else: **nodes are pure-ish, the runner is paranoid, the filesystem is the memory.**

## 2. The state schema

One dict, flat, with keys that mean one thing each:

| Key | Written by | Meaning | Why it exists |
|---|---|---|---|
| `topic` | caller | The input | The only domain input in this demo |
| `gathered_facts` | `node_gather` | `list[str]` | Output of node 1 |
| `attempts` | `node_process` | int | Retry counter **per node**, durable across restarts |
| `draft` | `node_process` | str | Intermediate artefact, not the answer |
| `final_output` | `node_finalize` | str | The answer |
| `next_node` | every node | str \| None | Control flow |
| `status` | caller / runner / finalize | str | `running`, `completed`, `failed_*` |
| `step_count` | runner only | int | Budget + trace numbering |

Note what is *not* in there: node functions, timestamps of the last run, exception objects, open file handles. Anything that cannot survive `json.dumps` does not belong in state. If you need it, put it in the log instead.

| 19 | `with open(temp_path, "w", encoding="utf-8") as f:` | Four decisions in one line. `with` guarantees the file is closed (and flushed) even if `json.dump` raises — without it, a serialisation error leaves a truncated file and an unflushed buffer. `"w"` truncates: we are rewriting the whole checkpoint each step. `encoding="utf-8"` is explicit because the platform default differs (cp1252 on this Windows box), and implicit encodings are the #1 cause of "works on my machine" file bugs. `as f` is the conventional handle name. | [`open()`](https://docs.python.org/3/library/functions.html#open), [The `with` statement](https://docs.python.org/3/reference/compound_stmts.html#the-with-statement), [Real Python: `with` Statement](https://realpython.com/python-with-statement/) |
| 20 | `json.dump(state, f, indent=2)` | `dump` (no `s`) writes to a **file object**; `dumps` returns a string you would then have to write yourself. `indent=2` is not decoration: checkpoints get opened by humans during incidents and by `git diff` during review, and a one-line JSON blob makes both useless. The cost is bytes on disk, which you can afford at 4 steps. | [`json.dump`](https://docs.python.org/3/library/json.html#json.dump), [Real Python: Working With JSON](https://realpython.com/python-json/) |
| 21 | `os.replace(temp_path, filepath)` | The commit. Rename-over-existing is atomic on POSIX, so a reader (or a resuming process) sees either the old file or the new one, never half of either. Deliberately **not** `os.rename` (fails or is non-atomic when the target exists on Windows) and **not** `shutil.move` (falls back to copy+delete across filesystems). Unindented, outside the `with`: the rename must happen only after the file is closed and flushed. | [`os.replace`](https://docs.python.org/3/library/os.html#os.replace), [Real Python: Reading and Writing Files](https://realpython.com/read-write-files-python/) |

**Why this is the single most important 5 lines in the file.** Without it, `Ctrl-C` mid-`json.dump` leaves a valid-looking JSON file with half a dict in it, and your "resume" feature resumes from corruption. With it, the worst case is a stale checkpoint plus a `.tmp` turd.

**What it still does not give you:** *durability*. `os.replace` is atomic with respect to visibility, not with respect to power loss — the data may still be in the OS page cache. If you need crash-of-the-machine safety, `f.flush(); os.fsync(f.fileno())` before the rename (§11). That is a real trade-off (a few ms per step), so it is a decision, not a default.

| 34 | `with open(log_filepath, "a", ..., newline="\n") as f:` | `"a"` = **append mode**: the OS seeks to end-of-file on every write, and on POSIX an `O_APPEND` write of a small buffer is atomic, so two processes interleave whole lines rather than shredding each other's bytes. `newline="\n"` is the subtle one: in text mode Windows translates `\n` → `\r\n`, which would leave a stray `\r` inside every record for downstream tools (and mixes line endings if the file is ever copied between OSes). **Why JSONL and not a JSON array?** An array must be rewritten (or at least re-parsed) to append, and one truncated tail byte makes the whole document unparseable. JSONL is append-only: a crash costs you at most the last, partial line, every earlier line is still valid, and `grep '"node": "process"'` works without a parser. This is the same reason application logs and telemetry pipelines use it.

**Cost you are accepting:** one `open`/`close` per step (~0.1 ms here, more on network filesystems), and no rotation — the file grows forever. Both are fine at 4 steps and wrong at 4 million (§11).

def changed_keys(before: dict, after: dict) -> list[str]:

## 10. Why *these* choices, and what you are giving up

You asked to understand the vocabulary, so here is the argument behind the whole shape — and the honest counter-arguments.

### Why a dict and not a dataclass?

A dict is already JSON-shaped. `json.dump(state)` works with zero adapters, and `state.get("x")` never explodes on an old checkpoint that predates a field. A dataclass (or `TypedDict`) buys you editor autocomplete and type checking, but costs you a serialisation layer (`asdict`, custom decoder) and makes schema evolution a code change rather than a missing key. The mature middle ground is `TypedDict`: it is *still a dict at runtime* but gives you static checking — see [Real Python: Data Classes](https://realpython.com/python-data-classes/) and [`typing.TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict). Do that when the schema stops changing weekly.

### Why strings in `next_node` and not function objects?

Because a checkpoint must be JSON. A function reference cannot be serialised, and a resume would have nothing to read. Strings also make the workflow *inspectable*: you can draw the graph from the trace, and you can diff two workflows as text. The cost is late binding (a typo fails at runtime), which you mitigate with constants or an `Enum` and a startup check:

```python
GATHER, PROCESS, FINALIZE = "gather", "process", "finalize"

for node in workflow_nodes.values():
    assert node({})["next_node"] in workflow_nodes or node({})["next_node"] is None
```

(That loop is illustrative — it calls every node with an empty state, which real nodes will not tolerate. The production-safe version is to declare edges as data: `EDGES = {"gather": {"process"}, ...}` and validate them once at import.)

### Why a `while` loop and not recursion?

A self-loop is iteration, not nesting. Recursion would grow the stack by one frame per step, make `max_steps` a recursion-limit accident, and — decisively — the checkpoint would only exist at the deepest frame, so a crash loses the whole call chain. The loop keeps the checkpoint at the top level, which is the only place it can be safely written.

### Why per-step checkpointing and not at the end?

Because the expensive thing in an agent is the *step* (an API call, an LLM call), not the loop. Re-running three steps because step four crashed is a cost you pay in money and latency. Per-step checkpoints make resume granular. The price is a `json.dump` per step — negligible for a dict, significant if your state holds a 5 MB transcript (see hardening below).

### Why both `status` and `next_node`?

`next_node` answers "what runs next?" — machine control. `status` answers "how did this run end?" — observability. Collapsing them into one field forces every consumer (dashboard, test, CLI) to interpret routing values as outcomes, which breaks the moment you add a branch. Two fields, two audiences.

### Why `run_agent` returns the state instead of raising on failure?

A completed-but-unhappy run (`failed_max_steps`) is *data*, and the caller may want to archive, retry, or display it. A programming error (unknown node) is an *exception*, because continuing would be meaningless. The boundary is: **can the caller do anything sensible with this value?** If yes, return it; if no, raise.

### When you should stop hand-rolling

You are still fine with ~10 nodes, one process, and human-scale volume. Reach for a framework or a different substrate when you need: durable execution across machines (Temporal, Prefect), parallel branches and fan-in, streamed token output, checkpoint versioning/migration, or a UI for humans-in-the-loop. The concepts you learned here transfer one-for-one — every one of those systems is still "state + edges + a log", just with more machinery around durability.

## 11. Hardening checklist (in the order I would actually do it)

| # | Change | Why | Where |
|---|---|---|---|
| 1 | Add `run_id` (uuid4) to state and every log record | Multiple runs in one directory are otherwise indistinguishable; also fixes duplicate step numbers after a crash between log and checkpoint | `starting_state`, `log_record` |
| 2 | `f.flush(); os.fsync(f.fileno())` before `os.replace` | Durability against power loss, not just process crash | `save_checkpoint` |
| 3 | Validate the loaded shape (`isinstance(d, dict)` and `"next_node" in d`) | A hand-edited or truncating disk yields a list `json.load` happily returns | `load_checkpoint` |
| 4 | Replace `os.path.exists` with `try/except FileNotFoundError` | Removes the TOCTOU race | `load_checkpoint`, cleanup block |
| 5 | Redact secrets before logging (`input_state` may contain API keys) | Logs are copied, shipped, and pasted into tickets | `run_agent` |
| 6 | `json.dumps(..., separators=(",", ":"))` and `ensure_ascii=False` | Smaller records; readable non-English text (default `ensure_ascii=True` escapes it) | `append_step_log` |
| 7 | Wrap `node_fn(state)` in `try/except Exception` → `status="failed_<node>"`, save, re-raise | Makes the checkpoint truthful when a node explodes | `run_agent` |
| 8 | Log `input_state`/`output_state` hashes, or only changed keys, when state is large | Full snapshots are O(n²) in total bytes across a long run | `log_record` |
| 9 | Use `time.perf_counter()` for `duration_ms` | Monotonic; immune to NTP/DST jumps. Keep `datetime` for `timestamp_start` | `run_agent` |
| 10 | Rotate or split the trace (`agent_trace.<run_id>.jsonl`), or move to SQLite | Append-only files never shrink; `sqlite3` gives you indexing and atomic transactions | `append_step_log` |
| 11 | Add a schema version field (`"schema": 2`) | Lets you migrate old checkpoints instead of guessing | `state` |
| 12 | Make the JSON strict: `json.dump(..., allow_nan=False)` | `NaN`/`Infinity` are emitted by default but are **not valid JSON** and break other parsers | `save_checkpoint` |
| 13 | Handle Windows `PermissionError` on `os.replace` (retry a few times) | Antivirus/editors can hold the target file open | `save_checkpoint` |
| 14 | Lock the state file if two processes may run the same run id | Two writers = last-writer-wins corruption | `save_checkpoint` |

Two notes on things people get wrong:

- **`os.replace` is atomic, not durable.** Atomicity protects *readers* from a half-written file. Durability protects *you* from a power cut. They are different guarantees and you need `fsync` for the second.
- **`json.dump` accepts `NaN` by default.** `json.dumps(float("nan"))` produces `NaN`, which Python reads back but strict JSON parsers reject. If any non-Python tool touches your files, pass `allow_nan=False`.

## 14. One-paragraph summary

State is a flat, JSON-serialisable dict. Nodes are functions from state to state that set `next_node`. The runner is a `while` loop that resolves `next_node` through a registry, guards the step budget, deep-copies the state before and after each call so the log records exact inputs and outputs, appends one JSON line per step, and only then atomically rewrites the checkpoint with `os.replace`. Crash-resume works because every routing decision is *in the file*, not in the process. Everything else in this guide is an explanation of why each of those clauses is worded the way it is.
